## DTrack 开发模块漏洞分析管理系统（初版完成）

在 `E:/workspace/python/DTrack` 用 Python 3.13 实现了模块化漏洞分析 CLI 系统。

### 架构（可扩展点）
- `dtrack/analyzers/`：`PackageAnalyzer` 接口 + `registry.py`。当前实现 `java`（解析 pom.xml + Maven 依赖解析）。后续加 `c/c++`、`docker` 只需新增 Analyzer 并在 registry 注册。
- `dtrack/vuln/`：`VulnerabilitySource` 接口 + `registry.py`。已实现 NVD(API 2.0)、GitHub Advisory(GraphQL, ecosystem=maven)、奇安信开源卫士(OpenAPI V3 `GET /open-api/v3/component/vulnerability`)。`aggregator.py` 合并多源、去重（按 CVE）、取最高严重度。
- `dtrack/sources/`：`SourceFetcher` 接口 + `registry.py`。已实现 GitLab / Nexus / Harbor（地址、凭据均可配置）。
- `dtrack/report/markdown.py`：生成 MD 报告（漏洞分布、组件明细、修复建议、依赖路径）。后续可换 Web 展示。

### 关键决策 / 坑
- 环境无 `mvn`：`MavenCentralResolver` 用纯 Python 拉取 Maven Central 的 pom 递归解析传递依赖（depth 上限可配）；若装了 mvn 则优先 `mvn dependency:tree`（`MvnTreeResolver`）。
- NVD 对 Maven 坐标无可靠 CPE：`nvd.py` 用多组 vendor 候选（org.apache.*→apache 等）+ product 去后缀猜测，合并结果。GitHub Advisory 才是 Maven 的可靠源（本环境 GitHub 被墙/超时，未实测）。
- 奇安信：`vuln/qianxin.py` 按手册实现；severity 映射 `qx_level_to_severity`（1-5 对应 超危/高危/中危/低危/未知，>5 按 CVSS 分数）。base_url 未配置时自动禁用。
- 配置文件 `dtrack.toml`/`dtrack.json`（TOML 用 tomllib），支持 `DTRACK__SECTION__KEY` 环境变量覆盖；CLI `config init` 生成示例。
- 循环导入已通过把 registry 拆到独立模块解决（analyzers/registry.py、vuln/registry.py、sources/registry.py）。

### 实测

## 需求：Java 分析剔除 junit 等测试组件

- 根因：单纯按 Maven scope 过滤不够——`log4j-core 2.14.0` 的 pom 把 `junit`/`mockito` 等**误标成 compile 作用域**（已知发布打包问题），纯 Python 解析会据此递归拉入整条测试依赖链（junit-vintage/jupiter/mockito/opentest4j…）。原 sample-java 因此解析出 26 组件（含大量测试依赖）。
- 方案：双层剔除。① scope 过滤（`analyze.exclude_scopes` 默认 `["test"]`，处理正确标注的 test 依赖）；② 名称过滤（`analyze.exclude_test_frameworks` 默认 True + `maven_resolver.TEST_FRAMEWORK_ARTIFACTS` 关键字表：junit/mockito/hamcrest/testng/spock/assertj/truth/easymock/powermock/scalatest/specs2/cucumber/selenide/arquillian/rest-assured/wiremock/json-unit/xmlunit/opentest4j/jmock/fest-assert），处理误标 compile 的测试框架）。
- 落地点：`maven_resolver.py`（MavenCentralResolver 直接+传递、MvnTreeResolver 均按 scope+名称跳过，并累计 `excluded_count`）；`java_analyzer.py` 做集中兜底过滤并汇总计数（active_resolver 透传）；`cli.py` 把剔除数量写入 `result.notes`（报告「备注」展示）。同时清理了 java_analyzer 里重复调用 MavenCentralResolver 的冗余代码。
- 配置：`config.DEFAULT_CONFIG` 新增 `analyze.exclude_scopes` / `analyze.exclude_test_frameworks`；可用 `DTRACK__ANALYZE__EXCLUDE_TEST_FRAMEWORKS=false` 等环境变量关闭名称过滤。
- 实测：sample-java 从 26 组件降为 5（3 直接 + 2 传递：log4j-api、spring-jcl），剔除 47 个测试相关依赖；log4j-core/commons-collections/spring-core 仍保留。测试：新增 test_direct_test_scope_excluded / test_direct_provided_scope_kept_by_default / test_test_framework_name_excluded；全量 28 单测通过。

## Bug 修复：奇安信 base_url 已填但仍报「缺少网关地址 vuln.qianxin.base_url」

- **真正根因**：TOML 嵌套表头写错。序列化器 `_to_toml` 递归时只写子表名（如 `[qianxin]`、`[nvd]`、`[gitlab]`），而 TOML 中 `[qianxin]` 是**顶层表**，不是 `[vuln]` 的子表。代码读的是 `vuln.qianxin.base_url`，但用户填的值落在顶层 `qianxin.base_url`，永远读不到 → 该源显示「已列入 vuln.sources 但未启用」。nvd/github/osv 因 DEFAULT_CONFIG 自带 api_url 仍可用，所以**只有 qianxin 炸**，极具迷惑性。

## Bug 修复：`mvn dependency:tree` UnicodeDecodeError + 解析为空/误解析

- **现象（用户截图）**：`UnicodeDecodeError: 'gbk' codec can't decode byte 0x80`；随后 `mvn dependency:tree 失败（unsupported operand type(s) for +: 'NoneType' and 'str'）` 触发回退。同时 `nvd/github/osv` 显示「已列入 vuln.sources 但未启用」。
- **根因 1（编码）**：`subprocess.run(..., text=True)` 在 Windows 中文环境默认按 GBK 解码，而 Maven 输出含 UTF-8 字符（如下载进度、BUILD 信息），导致 reader thread 解码失败；Python 3.14 内部处理该错误时又抛出 `TypeError: unsupported operand type(s) for +: 'NoneType' and 'str'`。
- **根因 2（-q 参数）**：`mvn dependency:tree -q` 会抑制 `[INFO]` 输出，导致 tree 返回空，解析为 0 deps 后触发「返回空结果」回退。
- **根因 3（误解析）**：`_TREE_LINE` 正则能匹配 BUILD SUCCESS 尾部行（如 `Finished at: 2026-08-17T15:30+08`），被当成组件；`direct=(depth == 0)` 把项目自身（根节点）也当成直接依赖。
- **修复**：`MvnTreeResolver.resolve()` 显式指定 `encoding="utf-8", errors="replace"`；去掉 `-q`；`_parse_line` 增加过滤（group 需含 `.`、不能含空格）；`resolve` 跳过 `depth==0`（项目自身），`direct=(depth == 1)`。
- **验证**：sample-java 正确解析 4 个第三方依赖（log4j-core/spring-core 为 direct，log4j-api/spring-jcl 为 transitive），不再出现 BUILD SUCCESS 伪组件；全量 28 单测通过。**已重建 `DTrack_offline.zip`（59 项）** 含修复。
- **关于 nvd/github/osv 显示未启用**：当前代码与 toml 均正确（`enabled()` 默认启用，除非显式 false）。截图中的未启用提示说明运行的是旧代码/旧离线包，重新解压最新 `DTrack_offline.zip` 即可恢复。

## Bug 修复：Windows 上 `mvn dependency:tree` 报 WinError 193 自动回退（实为路径 bug）

- **现象**：用户运行分析时日志打印 `mvn dependency:tree failed: [WinError 193] %1 不是有效的 Win32 应用程序`，随后回退纯 Python 解析。回退是**设计内的兜底**（java_analyzer 捕获异常后切 MavenCentralResolver），但 WinError 193 本身是**可修的 Windows 路径 bug**，不是 Maven 安装损坏。
- **根因**：`resolve_mvn_executable` 由 `maven.home` 推导时返回 `bin/mvn`，而 Windows 上 `bin/mvn` 是 bash 脚本，`MvnTreeResolver.available()` 用 `os.path.exists` 判定存在→尝试把它当 Win32 二进制直接 `CreateProcess`→WinError 193。真正的 Windows 启动器是 `bin/mvn.cmd`。
- **修复**：`resolve_mvn_executable` 在 `os.name == "nt"` 且由 home 推导时，按 `mvn.cmd`→`mvn.bat`→`mvn` 顺序返回首个存在的文件；显式 `maven.executable` 与无 home 的 PATH 情况保持原样。这样 Windows 上 `available()` 命中 `mvn.cmd`、`resolve()` 用 `mvn.cmd` 真正执行，不再触发 WinError。若 Maven 安装确有问题（如历史 ClassNotFoundException），仍会被现有兜底捕获并回退，行为不变。

## Bug 修复：奇安信 OpenAPI 查询返回 404

- **现象**：用户配置 `vuln.qianxin.base_url="https://10.131.122.120:80"`、basic 用户名/密码后，`QianxinSource.query` 收到 HTTP 404（nginx），返回空漏洞列表；相同账号可正常登录 Web。
