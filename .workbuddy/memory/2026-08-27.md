# 2026-08-27 工作日志

## 修复：白名单报告「影响项目」列 / 2.4 小节「markdown 有代码但输出无数据」+ PDF 报告缺章节

### 根因
1. **报告缓存未失效（主因）**：`service.py:get_report` 的 staleness 检测只看「分析目标」是否为旧的
   `ref_type:vid` 格式。报告若在「目标格式修复之后、2.4/影响项目功能之前」生成，格式已是新格式，
   于是直接返回旧 `report_md`，导致用户看到不含新章节的旧报告（看似「markdown 有代码但输出无数据」）。
2. **`projects_for_component` 取单一组件 id**：同一坐标在库中可能有 whitelist 行 + project 行两行，
   旧实现 `get_component(coord)["id"]` 取到 whitelist 行时会漏掉 project 维度的引用。
3. **PDF 报告从未同步**：`report/pdf.py` 独立构建各章表格、不读 `Component.extra`，所以既没有 2.4 小节，
   也没有第五章「影响项目」列（此前只改了 `markdown.py`）。

### 改动
- `dtrack/web/service.py`：`get_report` staleness 增加 `"### 2.4" not in md` 哨兵 → 缺新章节即重生成。
- `dtrack/web/store.py`：`projects_for_component(coord)` 改为按 `coord` JOIN 全部 `component` 行
  （`WHERE u.ref_type='project' AND c.coord=?`），正确处理同坐标双行。
- `dtrack/report/pdf.py`：新增 2.4 小节（产品(组件)|版本|最高严重度|中危及以上漏洞数|影响项目）；
  第五章组件全集表按 `show_affected` 条件追加「影响项目」列（仅当有数据时显示，避免无漏洞场景冗余）。
- `tests/test_report_affected_projects.py`：新增 3 用例——同坐标双行、`get_report` 缓存失效重生成含数据、
  PDF 报告含 2.4 与影响项目（PDF 文本以八进制转义+CID 编码，测试用 unescape+提取 ASCII 校验 `oa-system:1.0`）。

### 验证
- 端到端复现：写一份「缺 2.4 的新格式旧缓存」→ `get_report` 判定 stale 重生成 → 2.4 显示
  `org.apache.logging.log4j:log4j-core | 2.14.0 | 超危/严重 | 1 | com.demo:oa-system:1.0`；
  第五章「影响项目」列显示 `com.demo:oa-system:1.0`。数据非空。
- 全量单测 **100 个全部通过**（原 97 + 新增 3）。
- 注意：用户此前看到的「无数据」是缓存陈旧所致，非数据缺失；离线网关不可达仅影响真实扫描，不影响报告渲染。

## 前后端拉通 + 逆向测试（新增测试与 bug 修复）

### 新增测试
- `tests/test_web_integration_negative.py`（24 用例）：通过真实路由层 `_Router.dispatch` 与真实
  `http.server + Handler` 拉起 TCP 服务做 urllib 真实请求，覆盖导入/扫描/查询/报表（md+pdf）全链路，
  以及逆向场景（重复导入、不同镜像 owner、缺配置、缺字段、非法 JSON、越权静态路径、删除后访问、404 等）。

### 发现的 bug 与修复
1. **重复导入同一镜像/版本 500**：`store.py` 的 `add_*_version` 对 `(owner,version)` 唯一约束直接 INSERT，
   重导触发 `UNIQUE constraint failed` → 500。改为幂等 upsert：已存在则清空旧组件引用
   （新增 `_clear_version_usages`，`delete_version` 复用）+ 重置状态为 pending 重扫。
2. **不同镜像被错误合并到同一 owner、owner 名称错乱**：`service.py:_import_qianxin` 对 harbor/docker/gitlab-jar
   导入用 `upsert_whitelist(None, None, name)`/`upsert_project(None, None, name)`，导致不同镜像共享
   `(None,None)` owner 且名称被后写者覆盖。改为以制品名作 artifact_id（`upsert_*(None, owner_name, owner_name)`）。
3. **空 body / 无 pom 无 gitlab 导入静默建垃圾版本**：`_import` 增加
   `if not pom_text and not gitlab_project: raise ValueError(...)`。
4. **不存在的版本详情返回 200/null**：handlers 的 `/projects|whitelists/version/<id>` GET 在
   `get_version` 为 None 时返回 404。
5. **API 错误状态码不区分**：handlers 顶层 `except` 一律 500；改为 `ValueError`/`RuntimeError` → 400
   （输入/配置类错误），其余 → 500。
6. **PDF 与 Markdown「影响项目」列显示规则不一致**：`pdf.py` 的 `show_affected` 以
   `any(c.extra.get("affected_projects"))` 判定，而 `markdown.py` 以 `any(c.vulnerabilities)` 判定；
   白名单报告里「有漏洞但无项目引用」的组件在 markdown 有列、PDF 无列。统一为 `any(c.vulnerabilities)`。

### 验证
- 全量单测 **124 个全部通过**（基线 100 + 新增 24）。
- 新增测试覆盖：pom/harbor 全链路（含真实 HTTP 往返）、白名单报告影响项目列、静态越权路径拦截(403/404)、
  重复导入复用版本、不同镜像独立 owner、各类缺字段/缺配置 400、404 全链路、PDF 与 Markdown 列一致。

## 修复：第五章「影响项目」列对无漏洞组件误显

### 问题
用户反馈截图：第 26/30/32 行等组件「既无中危及以上漏洞，也无不安全 License，也标出了受影响的项目」。

### 根因
`service.py:_make_result` 对所有组件都注入 `affected_projects`；`pdf.py` 在第五章只要表格开了
「影响项目」列（`show_affected=True`），就会给**每一行**都填上影响项目，包括无漏洞组件。
`markdown.py` 的逻辑虽已在 `if c.vulnerabilities` 分支内处理，但防御性不够明确。

### 改动
- `dtrack/report/markdown.py`：将「影响项目」取值逻辑明确移到有漏洞分支外，无漏洞组件固定填 `—`，
  即使 `extra["affected_projects"]` 有数据也不显示。
- `dtrack/report/pdf.py`：在 `show_affected` 列追加处增加 `if c.vulnerabilities:` 判断，
  无漏洞组件固定填 `—`。
- `tests/test_report_affected_projects.py`：新增 2 个用例——markdown/PDF 均验证无漏洞组件
  （模拟截图中的 `cglib:cglib:3.3.0`）携带 `affected_projects` 时不会显示项目名。

### 验证
- 新增 2 个用例通过。
- 全量单测 **126 个全部通过**（基线 100 + 前后端拉通 24 + 本次 2）。

## 修复：第五章「影响项目」列仅对「中危及以上漏洞 / 传染型 License」展示

### 问题
用户反馈截图：第 8/9/11 行等组件「只有低危，无不安全 License，也列出了受影响项目」。
要求：只有中危及以上漏洞，或有不安全 License，才列出影响项目。

### 根因
上一轮修复只做到「无漏洞组件不显示」，但未区分漏洞严重度；低危漏洞组件仍被当作"存在漏洞"，
从而展示了影响项目。`show_affected` 判定也沿用 `any(c.vulnerabilities)`。

### 改动
- `dtrack/report/markdown.py`：新增 `_should_show_affected(c)` 判定——只有
  「存在中危及以上漏洞」或「传染型/不安全 License」才展示影响项目；
  `show_affected` 与每行数据均改用该判定。
- `dtrack/report/pdf.py`：导入 `_should_show_affected`，`show_affected` 与每行数据同步该规则。
- `tests/test_report_affected_projects.py`：新增 3 用例——
  低危组件不展示影响项目、传染型 License 组件展示影响项目、PDF 双通道均按此规则。

### 验证
- 新增 3 个用例通过。
- 全量单测 **129 个全部通过**（基线 100 + 前后端拉通 24 + 上轮 2 + 本次 3）。
